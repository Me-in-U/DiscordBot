# 음악 재생 상태와 비동기 처리

## 구조

`cogs/music/__init__.py`는 Cog 등록, 명령어, 이벤트와 공통 응답을 담당한다.
역할별 구현은 `favorites.py`, `panel.py`, `queue.py`, `requests.py`,
`controls.py`, `playback.py`에 있다. 공통 상수와 로거는 `runtime.py`에 있다.
기존 명령어 이름과 `MusicCog`의 호출 인터페이스는 유지한다.

챕터 이동과 2026년 10월 28일 로그 대응 변경은 [음악 및 외부 수집 오류 처리](runtime-errors-2026-10-28.md)에 정리했다. 해당 추가 변경은 실행 검증하지 않았다.

## 원인과 개선

### 이전 재생의 종료 콜백

음성 재생은 별도 스레드에서 끝난다. `stop()` 이후 콜백이 이벤트 루프에서
처리되기까지 지연이 생길 수 있다. 구간 이동 완료 시 `is_seeking`을 해제하면
이전 곡의 콜백이 새 곡을 종료된 것으로 처리할 수 있었다.

각 재생에 `playback_generation`을 부여하고 종료 콜백에 당시 값을 담는다.
구간 이동, 곡 교체, 정지 전에 이전 값을 무효화한다. 콜백은 길드 잠금을
획득한 뒤 식별자를 비교하고, 일치하는 종료만 한 번 처리한다.
같은 콜백이 반복 도착하거나 잠금을 기다리는 동안 재생이 바뀌어도
새 곡이나 대기열을 변경하지 않는다.

### 동시 재생 요청

재생 여부를 확인한 뒤 음원을 준비하는 동안 다른 요청도 즉시 재생을
시작할 수 있었다. 명령어, 검색 선택, 종료 콜백, 패널 확보와 대기 후
연결 해제를 길드별 `operation_lock`으로 순차 처리한다.

같은 길드의 두 URL 요청 중 첫 요청이 재생을 시작하면 다음 요청은
대기열에 들어간다. 정지는 진행 중인 음원 준비 작업 이후 처리되므로
정지 완료 후 준비 결과가 다시 재생을 시작하지 않는다. 다른 길드는
독립된 잠금을 사용한다. 검색 선택에서 URL 재생으로 이어지는 같은
작업은 잠금을 다시 획득하지 않아 교착을 방지한다.

음원 준비가 느리면 같은 길드의 정지도 그 작업을 기다린다.
추출 중단이나 즉시 취소 기능은 이 변경의 범위에 포함하지 않는다.

### 검색 응답 시간

일반 검색과 즐겨찾기 검색이 결과를 기다린 뒤 최초 응답을 보내면
Discord의 최초 응답 제한 시간을 넘길 수 있었다. 검색 전에 응답을
유예하고 결과는 후속 응답으로 전송한다. 이미 응답한 경우 중복 유예하지 않는다.

### 재생 중 패널 재열기

`/음악`과 재연결 시 패널 확보가 항상 기본 임베드와 대기 버튼으로
덮어쓰던 동작을 수정했다. 재생 중에는 재생 임베드와 제어 버튼을 유지한다.
일시정지 중에는 멈춘 시각으로 경과 시간을 계산한다.

### 진행 상태 갱신 작업

기존 작업 취소 후 공유 상태가 비워지기를 반복해서 기다리는 방식은
작업이 시작하기 전에 취소되면 끝나지 않을 수 있었다. 이제 이전 작업의
종료를 직접 기다린다. 이전 작업의 종료 처리는 자신이 현재 등록된
작업일 때만 상태를 비운다. 음성 연결 조회도 패널 메시지 대신 길드에서 한다.

## 재발 방지 테스트

`test/test_music_lifecycle_regressions.py`는 실제 Cog 메서드를 호출하고
음성 연결과 외부 검색을 가짜 객체로 대체한다. 이벤트로 작업 순서를
통제하여 다음 상황을 재현한다.

- 구간 이동과 곡 교체 이후 이전 콜백 도착
- 잠금을 기다리는 동안 재생이 바뀐 콜백
- 중복 콜백과 정상적인 마지막 곡 종료
- 동시 URL 요청에서 첫 곡 재생과 다음 곡 대기열 추가
- 음원 준비 중 정지 요청 이후 재생이 다시 시작되지 않는지 확인
- 일반 검색과 즐겨찾기 검색 이전 응답 유예
- 재생 중 또는 일시정지 중 패널 재열기
- 시작 전 취소된 갱신 작업의 재시작
- 검색 선택의 중첩 호출과 길드별 잠금 독립성
- 실패 시 잠금 해제와 분리된 Cog의 명령어 등록

소스 구조를 검사하는 기존 테스트는 분리된 구현도 읽도록 수정했다.
동시 실행 문제는 소스 문자열 검사만으로 판정하지 않고 실행 결과로 확인한다.

## 이전 커밋의 검증 범위 (`0ea198d`)

Python 3.11에서 다음 검증을 통과했다.

- 음악 관련 테스트 245개 통과, 새 실행 회귀 테스트 15개 포함
- 전체 테스트 789개 통과
- `bot.py`, `api`, `cogs`, `common`, `func`, `util`, `test` 문법 검사 통과
- 변경 사항의 공백 오류 검사 통과

외부 음원 다운로드와 실제 Discord 음성 재생은 수행하지 않았다.
로컬 테스트 통과는 Jenkins 실행이나 서버 배포 성공을 의미하지 않는다.


## 추가 예외 처리

다음 변경과 회귀 테스트는 추가했으며 아직 실행 검증하지 않았다.
위 검증 결과는 이 추가 변경의 통과를 의미하지 않는다.

- 종료 콜백의 오류를 전달한다. 반복 재생 오류는 스트림 주소를 갱신해
  한 번 재시도하며, 다시 실패하면 연결과 재생 상태를 정리한다.
- 시작 실패와 취소 시 준비된 소스를 정리하고 이전 콜백을 무효화한다.
  대기열은 유지해 다음 곡을 시도하고, 대기열이 없으면 자동 연결 해제를 예약한다.
- 정지는 음성 재생을 먼저 중단하고, 연결 해제 실패와 관계없이 상태를
  초기화한다. 패널 갱신 실패가 상태 정리를 막지 않는다.
- 기본 아바타만 있는 봇도 `display_avatar`로 임베드를 만든다.
- 진행 상태 갱신과 즐겨찾기 패널 갱신도 길드별 잠금을 사용한다.
  갱신 간 대기 시간에는 잠금을 해제한다.
- 음원 준비 실패와 마지막 곡의 패널 갱신 실패에도 자동 연결 해제를 예약한다.
- 즐겨찾기 재생은 DB 조회 전에 응답을 유예하고 DB 조회 오류를 안내한다.

추가 테스트는 시작 실패와 취소, 정지 중 연결 및 패널 오류, 반복 재생의
재시도 제한, 준비 실패, 기본 아바타, DB 오류와 패널 갱신 순서를 다룬다.

## 첫 곡 시작 시 오디오 준비

음성 채널 입장 후 첫 곡 시작 부분에서 소리가 끊기거나 급하게 들리는 현상의 유력한 원인은 FFmpeg 초기 출력 지연이 Discord 오디오 전송 시계에 포함되는 것이다. 실제 서버의 패킷 간격을 측정한 확정 원인은 아니다.

- FFmpeg Opus 프레임과 Ogg 페이지 출력 간격을 20ms로 지정한다.
- 재생 시작 전에 10개 패킷, 약 200ms의 오디오를 별도 스레드에서 준비한다. 준비한 패킷은 버리지 않고 순서대로 전송한다.
- URL 재생, HTML 대체 경로, 탐색, 캐시 URL을 사용하는 반복 재생에 동일한 준비 절차를 적용한다.
- 준비 제한 시간은 15초다. 빈 출력, 읽기 실패, 시간 초과 또는 취소 시 FFmpeg를 정리한다. 짧은 곡은 확보된 패킷을 그대로 재생한다.
- 준비 시간과 패킷 수를 기록한다. 이 버퍼는 시작 지연을 완화하며 지속적인 네트워크 지연까지 해결하지는 않는다.

`test/test_music_audio.py`에 패킷 순서와 보존, 이벤트 루프 밖에서의 읽기, 짧거나 빈 출력, 읽기 오류, 시간 초과, 취소 시 정리 테스트를 추가했다. 반복 재생 테스트도 버퍼 준비를 확인하도록 변경했다. 이번 변경의 테스트와 실제 Discord 재생 검증은 실행하지 않았다.
